## ข้อค้นพบจาก Content Studio

ภาพอ้างอิงแสดงว่าผู้ดูแลต้องกรอกค่าเชิงเทคนิค เช่น `Secondary href` เป็น `stores.html` และข้อความอธิบายใช้คำว่า `URL`, `media_assets`, `config` โดยไม่มีคำอธิบายปลายทางที่เข้าใจง่าย ภาพยังยืนยันว่าการอัปโหลดใช้ปุ่ม **เลือกจากคลังภาพ** และ **ถ่ายรูป** อยู่แล้ว ซึ่งสอดคล้องกฎการอัปโหลดของระบบ แต่ส่วนตั้งค่าปลายทางและสีต้องแปลงเป็นตัวเลือกภาษาไทย/ตัวเลือกภาพก่อนบันทึก โดยยังคงค่าที่บันทึกไว้เดิมเพื่อไม่ทำให้ลิงก์เดิมสูญหาย

### ผลทดสอบซ้ำจากเว็บไซต์จริง

- กด **ตรวจผู้รับ** บนคำขอถอนของ Rider `AImanusrider` แล้ว modal เปิดได้จริงและแสดงชื่อผู้รับ, โทรศัพท์, อีเมล, ประเภทผู้รับ และยอดถอนจาก response ของ Edge Function
- ในข้อมูลจริงคำขอดังกล่าวไม่มี `payout_snapshot` ที่บันทึกชื่อบัญชี ธนาคาร เลขบัญชี หรือ QR จึงหน้าจอแสดง `-` อย่างซื่อตรง ไม่สร้างข้อมูลสมมติขึ้นมา
- ผลนี้ยืนยันว่า workflow เปิดรายละเอียดทำงานบน session Admin จริงแล้ว แต่ยังต้องให้ flow การสร้างคำขอถอนเก็บ payout snapshot ให้ครบ และต้องทดสอบ guard ของปุ่ม **บันทึกโอน** โดยไม่กดยืนยันการโอนจริง

## หลักตรวจรับ

- ตรวจหน้าและปุ่มใน browser ด้วย session Admin จริงก่อนสรุปผล
- ไม่รายงานผลจากการ build หรือจาก DOM เพียงอย่างเดียวว่าเป็นการทำงานแบบ end-to-end
- ใช้ข้อมูลว่างจริงเป็น empty state และไม่สร้างข้อมูลจำลองเพื่อให้การตรวจดูเหมือนผ่าน

## หลักฐาน backend ของคำขอถอนเงิน

- Supabase project ที่เว็บไซต์ใช้งานจริงคือ `abtsctwfkgzciseppach`; Edge Function `role-access` สถานะ `ACTIVE`, version 21
- Source ที่เผยแพร่มี action `get_withdrawal_review_detail` อยู่จริง โดยอ่านคำขอถอนพร้อมผู้รับ, snapshot บัญชีปลายทาง, สถานะ, หลักฐาน, เลขอ้างอิง และเวลา `requested_at`/`reviewed_at`/`paid_at`
- Action ดังกล่าวตรวจสิทธิ์ผู้เรียกเป็น Admin และเติมข้อมูลผู้รับจาก Rider หรือร้านค้า รวมถึงชื่อ โทรศัพท์ อีเมล และที่อยู่
- ข้อแก้ไขที่ถูกต้องคือทำให้ frontend เรียก action นี้ด้วยสัญญาข้อมูลที่ backend รองรับ แล้วตรวจ response ต่อ session Admin จริง; ห้ามสร้างข้อมูลจำลองในหน้า Finance
- การบันทึกโอนต้องคง RPC `admin_review_withdrawal` ที่บังคับหลักฐานการโอนและเลขอ้างอิงก่อนสถานะ `paid` พร้อมแสดงข้อมูลและเวลาสำคัญให้ผู้ดูแลตรวจได้

## บัญชีและสิทธิ์

- ตรวจหน้า `https://apirak272543-ship-it.github.io/Apservicebeta/admin/profile.html` เมื่อ 20 สิงหาคม 2569 พบ **404** เพราะไม่มีไฟล์ `profile.html` ใน repository ขณะที่หน้าจัดการบัญชีที่เผยแพร่จริงคือ `accounts.html`
- เปิด `accounts.html` ด้วย session Admin สำเร็จ พบตัวกรองทุกบัญชี/Admin/ลูกค้า/ร้านค้า/Rider และปุ่มเพิ่มบัญชี แต่ต้องรอให้ Account Control Plane โหลด และต้องเพิ่มเส้นทาง compatibility สำหรับ `profile.html` เพื่อไม่ให้กลายเป็น dead link
- หลัง Account Control Plane โหลด หน้าแสดงบัญชีจริง 15 รายการ, รองรับค้นหาด้วยชื่อ/อีเมล/โทรศัพท์/Login ID/รหัสผู้ใช้ และกรองตามบทบาทได้
- กด **จัดการบัญชี** บนรายการจริงแล้วเปิด modal ของบัญชีได้ ไม่เป็นปุ่มตาย; ระหว่างตรวจไม่ได้บันทึกหรือแก้ไขข้อมูลบัญชีจริง

## ตัวเลือกตำแหน่งร้าน

- หลังเปิดฟอร์มเพิ่มร้านบน `stores.html` ที่เผยแพร่จริง พบว่าฟอร์ม Store Control Plane สร้างด้วย `form[data-form]` ขณะที่ตัวเลือกแผนที่เดิมค้นหาเฉพาะ `form[data-store-form]` จึงไม่ถูกติดตั้งและผู้ใช้เห็นเฉพาะช่องละติจูด/ลองจิจูด
- แก้ตัวติดตั้งให้ตรวจทั้งฟอร์มเดิมและฟอร์มที่ Store Control Plane สร้างจริง แต่ติดตั้งเฉพาะเมื่อมี `location_lat` และ `location_lng` ครบ เพื่อไม่กระทบ modal อื่น
- หลังเผยแพร่ต้องเปิดฟอร์มเพิ่มร้านและยืนยันว่าปุ่ม **เลือกจากแผนที่** และแผนที่ Leaflet แสดงขึ้น ก่อนทดสอบเลือกพิกัดจริง
